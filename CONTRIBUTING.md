# Contributing

Thank you for considering a contribution to HarnessMark. This document covers adding harnesses, repos, and frozen task sets, plus the ground rules for changes to the benchmark itself.

Read [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) first.

## Ground rules

- Zero npm dependencies. Node 24+, ESM, `node:` builtins only.
- `harness/contracts.md` is the interface. Change it deliberately and update every consumer in the same commit.
- Tests are plain scripts. Run them all before opening a change:

```
for t in evaluator/test/*-test.mjs harness/test/*-test.mjs report/test/*-test.mjs \
         runner/test/*-test.mjs harness/reference/test/reference-test.mjs \
         spike/test/lang-classify-test.mjs spike/test/negative-control.mjs spike/test/wt-test.mjs \
         tools/test/notices-test.mjs; do
  node "$t" || exit 1
done
```

## Adding a harness

1. Discover the harness's real headless mode with `<cli> --help`. Do not invent flags.
2. Create `adapters/<name>.mjs` exporting `{name, version, run({prompt, dir, model, budgetMs, outDir, stateDir})}`
   per the Adapter API in `harness/contracts.md`.
3. Write the full raw stdout and stderr to `transcript_path`. Report telemetry as `null` when the harness
   does not emit it, never `0`.
4. Kill the process group when `budgetMs` elapses. macOS has no `timeout` binary.
5. Derive `topology` from the transcript with `harness/topology.mjs`. If the harness emits pi-shaped
   events, `topologyFromTranscript` handles it; otherwise add an analyzer and tests.
6. If the harness keeps local state (index, code graph, cache), read `BENCH_STATE_DIR` and export
   `statePaths` for anything it writes inside the repo.
7. A configuration is a harness. Label non-default arms (`pi-solo`, `claude-xhigh`) through an environment
   variable the adapter reads; never merge them into the default rows.
8. Smoke it: `node runner/run.mjs --set dev-immer-12 --limit 1 --adapter <name> --model <m> --out runs/_smoke`.

## Adding a repo

1. Register it in `harness/registry.mjs` with `lang`, `reporter`, `install`, `testCmd`, `testArgs`, `image`.
   Mark it `status: "candidate"`.
2. Add a Dockerfile under `docker/<repo>/`.
3. Harvest: `node spike/harvest.mjs <repo>`. The harvester validates every oracle at the parent and the fix.
4. Precompute baselines: `node runner/run.mjs --repo <repo> --task all --baseline-only --out runs/_baselines-<repo>`.
5. Only when the repo has validated tasks and cached baselines does it move to `status: "active"`.

## Frozen sets

Sets under `sets/` are generated by a rule in `harness/sets.mjs`, never hand-edited. To propose a new set,
add a rule and run `node harness/sets.mjs --generate <name>`. A published set never changes; bump the
version and freeze a new one.

## Reporting results

Runs whose directory name begins with `_` are excluded from the leaderboard. Everything else under `runs/`
is picked up by `node report/leaderboard.mjs`. Before sharing a run directory, scan its transcripts: they
carry absolute paths and raw provider error text.

## Submitting harness results

To propose a new row on the public leaderboard:

1. Run the benchmark on a frozen task set with `--trials 5` (minimum).
2. Verify the run completed: `node report/report.mjs runs/<your-run>`.
3. Open an issue with the run configuration, the reported numbers, and a link to the full `results.jsonl` and transcripts (upload as a zip or host them). Do not paste raw transcripts into the issue.
4. A maintainer will review the configuration and may independently reproduce the run before merging the result.

See [docs/METHODOLOGY.md](docs/METHODOLOGY.md) for what gets excluded and how lift is computed.
